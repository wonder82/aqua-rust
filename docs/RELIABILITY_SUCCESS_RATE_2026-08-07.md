# 成功率提升方案（生产实测驱动）

> 日期：2026-08-07
> 依据：网关 24h 真实数据 + OpenAI/LiteLLM/new-api/one-api 官方最佳实践

---

## 一、现状实测（24h 网关 request_logs，共 24715 条）

| 状态码 | 数量 | 占比 | 平均延迟 | 分类 |
|---|---|---|---|---|
| 200 | 18658 | 75.5% | 26.0 s | 成功 |
| 404 | 1475 | 6.0% | 0.23 s | **客户端模型名错误** |
| 500 | 1443 | 5.8% | 0.45 s | **bge-m3 嵌入上游故障** |
| 503 | 1838 | 7.4% | 4.9 s | 上游耗尽/不可用 |
| 410 | 798 | 3.2% | 0.13 s | 客户端调用已弃用模型 |
| 400 | 397 | 1.6% | 5.8 s | 客户端参数错误 |
| 502 | 97 | 0.4% | 242 s | 读取上游响应超时 |
| 403/429 | 9 | <0.1% | ~0.2 s | 上游拒绝 |

**真实成功率** = 75.5%。若排除客户端自身问题（404+410+400=2670，占 10.8%）与单模型故障（bge-m3 500=1443，占 5.8%），**网关可控制范围内的成功率可达 91%+**。

## 二、逐类根因分析

### 2.1 503「上游耗尽」1838 条（最关键）
错误样本：
- deepseek-ai/deepseek-v4-pro：665 条 `upstream conn: error sending request`（连接错误）
- nvidia/llama-3.1-nemotron-nano-vl-8b-v1：654 条 `cannot identify image file`（客户端图片格式错误被 NIM 以 500 返回，重试 3 次后 503）
- minimaxai/minimax-m3：254 条真实 429
- openai/gpt-oss-120b：119 条真实 429
- nemotron-550b：52 条 Worker 饱和 500

**根因**：
1. [scheduler.rs](src/gateway/scheduler.rs) `record_response()` 对**首次 429 即冷却 1 小时**（`COOLDOWN_429_SECONDS=3600`），模型范围组内密钥有限，429 一多整组全冷 → 该模型 1 小时内持续 503。
2. 连接错误 `conn_error` 冷却 30s 且 `select_key()` 按"最少使用优先"轮转——若大量 key 同时出现连接错误（如 NVIDIA 某时段网络抖动），会迅速击穿整个池。
3. 客户端发坏数据（坏图片等）→ NIM 返回 500 → 我们重试 3 次白费 token 与时间 → 最终 503。

### 2.2 500 1443 条 = bge-m3 单一模型故障
全部为 `baai/bge-m3` 嵌入请求，上游固定返回 `{"error":"Something went wrong with the request."}`。**模型级熔断器未触发**（[circuit.rs](src/gateway/circuit.rs) 阈值 5xx=50，但该错误是 500，每次请求重试 3 次 = 一个用户请求产生 3 次计数……实际上熔断器按 model 维度记录，50 次窗口应会触发；但窗口 30s 重置 + 每次重试都 `record_failure`，看起来未及时切断）。

### 2.3 404 1475 条 = 客户端模型名过期
客户端仍在调用已下架/更名的模型（如 deepseek-coder-6.7b、llama3-chatqa、kimi-k2.6、bge-m3 外的旧模型等）。非网关故障，但**在成功率的用户观感上造成伤害**。

### 2.4 410 798 条 = 已弃用模型
我们主动拦截（正确行为），但客户端未更新。

## 三、优化方案（按优先级排序）

### P0-1 429 冷却策略重构（对标 LiteLLM cooldown / new-api 故障转移）
- **做法**：
  1. **首次 429 冷却改为 30-60s**（不是 1h）；连续 429（如 5 次/窗口）才升级为 10min 冷却；整体打满 240 key 池（"all keys cooling"）时**降级放行**最健康 key，保证服务可用；
  2. 冷却时间**指数级退避**：30s → 60s → 120s → 300s → 600s，每次成功降一级；
  3. 管理后台提供「一键重置全部冷却」。
- **代码位置**：`constants.rs`（COOLDOWN_429_SECONDS 分级）、[scheduler.rs](src/gateway/scheduler.rs) `record_response()` 429 分支。
- **收益**：deepseek/gpt-oss 类高峰 429 不再造成 1h 局部不可用，503 显著下降。

### P0-2 模型级熔断阈值调低 + 错误类型细分（对标 gobreaker 语义）
- **做法**：
  1. `CB_FAILURE_THRESHOLD_5XX` 从 50 → **10**，窗口从 30s → 60s；
  2. 熔断器按「错误类型 × 模型」独立计数：`upstream 4xx(非404)`、`5xx`、`conn_error` 分开；**4xx 客户端错误（400/404/410/422）不参与熔断计数**（否则坏客户端会打爆熔断器）；
  3. 熔断 OPEN 时返回 **502 + `model_overloaded` 业务码**，并标记该模型「暂不可用」到模型列表（用户前台可见）。
- **代码位置**：`constants.rs`、[circuit.rs](src/gateway/circuit.rs) `record_failure()`。
- **收益**：bge-m3 类单模型故障在 ~10 个请求内切断，不再拖累整体成功率与日志噪音。

### P0-3 上游错误响应透传（不再重试客户端错误）
- **做法**：
  1. `should_retry()` 严格化：**仅 429 / 502 / 503 / 504 / 连接错误 重试**；400/404/410/422 等**立即透传**；
  2. 对 5xx 重试也**限制在 2 次**；
  3. 重试次数按错误类型差异化（对标 LiteLLM `retry_policy`：RateLimitError→5、TimeoutError→2、InternalServerError→3）。
- **代码位置**：[public.rs](src/gateway/handler/public.rs) `should_retry()` + 重试循环。
- **收益**：坏图片/坏参数请求不再白烧 3 次重试（省 654 条×3 的无效上游调用），失败响应时间从 5s → 0.2s，且用户拿到的是**明确的上游错误**而非笼统 503。

### P1-1 模型健康度巡检与自动下架（运维自动化）
- **做法**：后台定时任务每小时统计各模型近 1h 成功率：
  - 成功率 < 50% 且请求数 > 50 → **自动标记「上游故障」**并从前台模型列表隐藏/置灰（同弃用模型处理），人工确认后恢复；
  - 恢复条件：近 30min 成功率 > 90%。
- **代码位置**：复用 `console.rs` 模型监控数据结构 + 新增后台 task。
- **收益**：bge-m3 这类故障 1h 内自动隐身，用户不再遇到 500。

### P1-2 客户端引导（降低 404/410/400 占比 10.8%）
- **做法**：
  1. 404 响应体中附**推荐替代模型**（`build_model_error_suggestion` 已有），并追加 `X-Suggested-Model` 头；
  2. 在用户控制台模型列表顶部展示「近期已下线模型」公告；
  3. 对高频 404 客户端（IP/密钥维度）推送站内信。
- **收益**：客户端更新模型后，404+410 占比从 9.2% 快速趋近 0，整体成功率 +9%。

### P2-1 嵌入端点独立熔断与降级
- **做法**：嵌入模型（bge-m3 等）使用**独立的熔断实例**与失败策略（嵌入失败直接透传，不重试 3 次——嵌入无生成过程，重试无收益）。
- **收益**：1443 条 bge-m3 500 不再产生 3 倍日志与重试开销。

## 四、预期收益汇总

| 优化项 | 消除的失败 | 成功率提升 |
|---|---|---|
| 429 冷却重构 | 高峰模型 1h 局部宕机 | +3~5% |
| 熔断阈值调低 | bge-m3 类故障扩散 | +5.8% |
| 客户端错误快速失败 | 654 条无效重试 | 失败响应变快 |
| 自动下架巡检 | 持续故障模型 | +2~5% |
| 客户端引导 | 404+410 | +9%（客户端配合） |
| **合计目标** | — | **75.5% → 88~93%** |

## 五、监控建议

- 网关管理后台「全局状态」增加：模型成功率 TOP10 / 故障模型自动标记列表 / 冷却中密钥数；
- 成功率的统计口径建议改为**排除客户端错误**（404/410/400 不计入网关 SLA），避免误判；
- 为每个模型建立「连续失败计数」告警：单模型 5 分钟内 5xx+conn 错误 > 20 次触发钉钉/邮件告警。

> 所有常量变更需遵循 `docs/constants.md` 审批流程。P0 三项均为低风险参数/逻辑调整，可独立灰度验证。
