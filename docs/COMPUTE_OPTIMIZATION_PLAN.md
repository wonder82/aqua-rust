# AQUA 网关 · 算力更新迭代规划

> 版本：v1.0（待审核）
> 日期：2026-08-11
> 状态：**规划草案，未实施**。审核通过前不做任何代码改动。

---

## 1. 背景与目标

### 1.1 问题反馈
用户集中反馈：**英伟达（NVIDIA NIM）上游模型**经常出现：
- **请求失败**：偶发 4xx/5xx、连接中断；
- **无反应**：请求发出后长时间没有响应，几分钟不吐一个字节；
- **速度过慢**：首字延迟（TTFT）高，流式回复卡顿。

### 1.2 优化目标
| 指标 | 当前基线 | 目标 |
|---|---|---|
| 上游请求失败率 | 高（依赖用户反馈） | ≤ 2% |
| 卡死/无反应占比 | 有（无看门狗） | 0（所有路径都有超时兜底） |
| 用户端最长等待（失败时） | 最坏约 15s+（重试退避累积） | ≤ 8s 快速失败并提示 |
| 单密钥并发 | 可被突破至 8+ | 严格 ≤ 8（信号量硬限） |
| 密钥池利用率 | 粘性轮转，部分 key 闲置 | 全部 key 参与加权均衡 |

### 1.3 一句话定位
不是"绕过限制去抢算力"，而是**在 NVIDIA API 服务条款允许的范围内，用调度算法把现有算力资源的可用性、吞吐与公平性做到最优**——把池子里每个密钥的算力都榨出来，同时避免任何违规动作。

## 2. 现状诊断（代码事实）

以下问题点来自对 `scheduler.rs / detect.rs / circuit.rs / model_health.rs / handler/public.rs / constants.rs` 的代码核查：

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| P1 | 网关 SSE 流式路径**无空闲看门狗**，`stream_client` 无整体超时 | `handler/public.rs:669-733` | 上游卡死 → 用户"无反应"，密钥在途计数永久占坑 |
| P2 | 特殊/专线密钥**绕过全部健康保护**（冷却/健康度/在途/RPM），失败连打 5 次带退避 | `scheduler.rs:283-302` | "请求失败 + 速度慢"的直接来源 |
| P3 | 候选耗尽时 **fallback 突破并发上限** | `scheduler.rs:234-253` | 高负载下单 key 并发超 8，加剧上游 429/过载 |
| P4 | 用户侧**并发计数 / RPM 限流 / 异常计分全部未接线**（有实现无调用），`GLOBAL_CONCURRENCY_LIMIT=20` 形同虚设 | `detect.rs`、`scheduler.rs:430-442` | 流量可无上限涌入上游 |
| P5 | 密钥健康评分基于**进程累计**而非滑动窗口，对近期劣化反应迟钝 | `scheduler.rs:406-428` | 坏 key 不能及时被隔离 |
| P6 | 多协议入口（/v1/messages、/v1/responses）`reqwest::Client::new()` **无任何超时** | `handler/public.rs:900` | 上游挂起 → 请求挂死 |
| P7 | 全部 key 不可用时"尽力而为"放行健康度最高 key + 5 次重试 + 最长 15s 退避 | `scheduler.rs:234-253`、`public.rs:387-523` | 失败延迟被放大到用户可感知 |
| P8 | 熔断器刻意忽略 429 与连接错误；流式成功在**收到 200 头即记账**，掩盖真实故障 | `circuit.rs:105-109`、`public.rs:456` | 故障率被低估 |

## 3. 合规边界（"抢算力而不违规"的红线）

所有优化必须满足：

**允许（正常运营手段）**
- 多密钥池轮询、健康感知调度、并发池控制、平滑限流、超时保护、指数退避重试
- 在 API 返回 429 时遵守 `Retry-After`，尊重上游限速语义
- 对慢/坏上游快速失败并降级，保护上游不被压垮

**禁止（违规动作）**
- ❌ 绕过/伪造认证、破解鉴权、盗用他人密钥
- ❌ 无视 429 强行并发风暴、恶意打爆上游
- ❌ 伪装 UA / 伪造请求指纹规避平台风控
- ❌ 批量注册/养号绕过配额

> 原则：**优化调度是"把力气用在刀刃上"，不是"作弊"**。上游限速是公平使用保护，我们通过更聪明的调度在合法上限内达到最优吞吐，同时不伤害上游与其他用户。

## 4. 迭代规划（分四期，每期可独立上线、独立回滚）

### 第一期：稳定性止血（直接解决"无反应/几分钟不回复"）

**1.1 全链路超时分层**（改 `constants.rs` + `handler/public.rs`）
- 新增：连接 10s / 首字节（header）30s / SSE 块空闲 45s / 非流式整体 120s
- 多协议入口改用带超时的 `http_client`（修 P6）
- 失败时向客户端写明确的 `upstream_timeout` 错误事件，而非无限挂起

**1.2 SSE 空闲看门狗接入网关路径**（复用 `sse.rs` 的 `stream_proxy` 思想）
- 流式读循环用 `tokio::select!` 加空闲超时（修 P1）
- 空闲超时触发时：中断连接、释放密钥在途计数、标记该 key 一次失败
- 流式成功记账从"收到 200 头"改为"收到 `[DONE]` 或完整响应体"（修 P8）

**1.3 特殊/专线密钥纳入健康保护**（改 `scheduler.rs:283-302`）
- `select_special_key` / `select_line_key` 增加：冷却中跳过、失败计数、在途上限
- 特殊密钥失败**不连打 5 次**，改为"同池内换一个（如存在）或快速失败"（修 P2）

**1.4 快速失败替代重试风暴**（改 `public.rs` 重试循环）
- 普通模型重试上限 5 → 3；连接类错误 fast_retry 保持
- 退避上限 8000ms → 3000ms；全部 key 不可用时不"尽力而为"放行坏 key（修 P7）
- 引入 `max_total_wait`（默认 8s），超时直接返回 503 `upstream_busy`，文案明确"请稍后重试"

**验收**：压测上游人为断流时，所有请求在 ≤8s 内得到明确响应；无永久挂起连接；在途计数无泄漏。

---

### 第二期：调度算法升级（"抢算力"核心，让每个 key 都干活）

**2.1 滑动窗口健康评分**（改 `scheduler.rs:406-428`）
- 弃用进程累计，改为 **1 分钟滑动窗口**记录成功率 / 平均 RT / 429 率 / 5xx 率
- 评分公式（沿用现有权重）：
  `score = 成功率40% + RT20% + 429率20% + 5xx率20%`
  - RT 评分：500ms=100 分，10s=0 分（线性）
- 每分钟衰减（`score = score * 0.9`），近期劣化 1-2 分钟即可反应

**2.2 加权健康感知轮询**（改 `select_key`）
- 候选排序改为：**健康分高者优先 + 最少在途优先 + 最久未用优先** 三级排序
- `weight` 从"仅放大轮转阈值"升级为**参与加权概率**：健康 key 按 weight 加权抽取，坏 key 权重自动归零
- 修 P5：坏 key 及时隔离，好 key 承接流量

**2.3 并发硬限：信号量 + 严格拒绝**（改 fallback 分支）
- 每 key 用 `tokio::sync::Semaphore(8)` 硬限并发（修 P3），`begin_request` 改为 `try_acquire`
- 获取不到并发：**跳过该 key**，绝不突破；全部 key 无并发 → 直接快速失败（不再 fallback 硬打）
- 客户端级并发计数接线（`record_client_request` 等已存在，启用即可，默认每客户端 5 并发上限，可配置）

**2.4 平滑限流：令牌桶接线**（启用 `detect.rs::RpmBucket`）
- 每密钥 RPM 平滑（现有 60s 窗口 → 令牌桶按秒补充），平滑突发、避免上游 429
- 客户端侧 RPM 限流启用（默认 120 RPM，可配置），超限返回 429 + `Retry-After`

**2.5 新密钥预热**（修"预热机制形同虚设"）
- 新密钥 `warmup_progress` 从 0 开始，前 20 次请求逐步放开并发（1→8），避免新 key 冷启动打爆上游

**验收**：单 key 并发恒 ≤8；坏 key 被隔离后成功率提升 ≥50%；全池密钥使用率 >80%；上游 429 率下降。

---

### 第三期：智能降级与容灾

**3.1 多上游容灾（未来预留）**
- 配置化支持"同模型多上游"，失败自动切换备用上游（NVIDIA → 备用渠道）
- 仅在有第二个合规渠道时启用，不硬编码任何凭证

**3.2 模型降级链（配置化）**
- 可选：`model_fallback_chains` 表，如 `deepseek-v4-pro → deepseek-v4-flash`
- **默认关闭**，仅对明确标注"可降级"的模型生效（避免用户困惑：模型变了要有提示）

**3.3 自愈与运维**
- 实现 `HEAL_*` 常量的自愈逻辑：熔断 OPEN 的 key 定时探测恢复，恢复后自动回池
- `unfreeze` 接口同时清除内存冷却（修 admin.rs:495-507）
- 增加 `/gw/admin/upstreams/health` 一键查看全部 key 的滑动窗口健康分/在途/冷却

**验收**：坏 key 自愈回池无需人工；管理员可实时查看调度器内部状态。

---

### 第四期：可观测性与持续优化

**4.1 调度指标暴露**（新增 `/gw/admin/scheduler-metrics`）
- 每 key：成功率/平均 RT/429/5xx/在途/冷却状态/健康分（滑动窗口）
- 全局：总在途、每秒请求、重试次数、快速失败次数、上游 429 计数

**4.2 慢上游预警**
- 每分钟扫描：TTFT 均值 > 60s 或失败率 > 10% 的 key/模型 → 管理后台预警 + 自动降权

**4.3 A/B 验证**
- 调度参数（并发上限、重试次数、退避上限、RPM）全部可配置，支持灰度对比
- 用 4.1 的指标做前后对比，逐步调参

## 6. 风险与回滚

- **风险**：并发硬限/快速失败可能短暂提高"被拒请求"数（从慢变快拒）→ 用 4.1 指标监控，参数可调
- **风险**：滑动窗口评分在冷启动期样本不足 → 样本 <30 时保持默认分并放行
- **回滚**：所有参数均可在 `constants.rs`/配置关闭；单期改动 git 独立 commit，回滚 = revert 对应 commit + 滚动热更
